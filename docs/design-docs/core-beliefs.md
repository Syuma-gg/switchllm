# 基本方針

判断に迷ったときの拠り所。個別の判断は [index.md](index.md) にある。

## なぜ作るのか

AI プロバイダーごとに SDK もリクエスト形式も違うので、モデルを変えるたびにコードを直す必要がある。クライアント側の1か所（モデル文字列）を変えるだけで切り替えられるようにしたい。

同じ目的の OSS（LiteLLM、mozilla-ai の any-llm など）は既にある。それでも作る理由は3つ。

- 中身を理解できる薄さにする
- 依存を httpx だけにする
- 自作エージェントの LLM 層として、プロバイダー固有の情報（署名・推論）を落とさずに使う

本番運用だけが目的なら LiteLLM の方が適切、という前提は共有している。

## 方針

1. **薄く保つ。** 共通化するのは、どのプロバイダーでも意味が揃うものだけ。揃わないものは `extra=` で各社の形式のまま渡してもらう。機能を足す前に [スコープ](../product-specs/scope.md) を確認する。
2. **依存は httpx だけ。** 各社の SDK は使わない。
3. **情報を落とさない。** プロバイダーが返したものは、同じモデルへ送り返すときにそのまま返す。
4. **黙って無視しない。** 対応できない指定は `UnsupportedFeatureError`、変換できない型は `TypeError` にする。期待と違う動きを静かにするより、早く失敗する。
5. **約束は小さく。** 公開 API、プリセット、自動変換できる型は、保守し続けられる範囲だけを約束する。足すのは後からでもできるが、消すと利用者のコードを壊す。
6. **使い心地は下げない。** 削るのは保守の約束であって、よく使う便利さではない。迷ったら「残したうえで範囲を固定する」を先に検討する。
7. **一次情報で確かめる。** API の形式は各社の公式ドキュメントで確認し、出典を [references](../references/index.md) に残す。確かめていないことは「未検証」と書く。
8. **テストはネットワークなしで速く。** 実 API での確認は `scripts/smoke_test.py` に分け、料金が発生することを明示する。
9. **検査の数字のために品質を落とさない。** 検査は品質を上げるための手段。基準を緩めたり、黙らせたりして通さない（[品質検査の方針](quality-gates.md)）。
