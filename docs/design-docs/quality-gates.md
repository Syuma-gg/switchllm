# 品質検査は品質を上げるためにあり、数字を通すために品質を落とさない

- 状態: 採用（2026-11-14）
- コード: `scripts/quality_gate.py`、`.claude/settings.json`（Stop フック）、`.github/workflows/test.yml`（`quality` ジョブ）
- 基準: `pyproject.toml` の `[tool.ruff.lint]` と `[tool.coverage]`
- テスト: `tests/test_quality_gate.py`

## 背景

AI にコードを書かせると、検査の数字（ruff の違反 0 件、カバレッジ）を満たす一番の近道を選びやすい。行を実行するだけで結果を確かめないテストを書く、`# noqa` や `# pragma: no cover` で黙らせる、基準の値を下げる、落ちるテストを消す、などである。どれも検査は通るが、品質は上がらないか、かえって下がる。

検査を確実に回すには、モデルの判断に任せる仕組み（skill や指示だけ）では足りない。一方で、仕組みだけでは「どう直すか」の判断は伝わらない。

## 決定

### 原則

1. 検査は品質を上げるための手段。数字を通すことを目的にしない
2. テストには振る舞いを確かめる assert を書く。行を実行するだけのテストは書かない。テストを書いて見つかった不具合は直す
3. 基準（`fail_under`、ruff のルール、カバレッジやテストの除外）を緩めない。緩める必要があると考えたら、理由を説明してユーザーの了承を得る
4. `# noqa`・`# pragma: no cover`・`pytest.mark.skip` / `xfail` は、品質上の理由があるときだけ使う。コメントで書くものには、同じ行に理由を書く（例: `# noqa: B006 - 可変の既定値でも任意の引数として扱えるか確かめる`）。使ったことは作業の報告で伝える
5. 品質を落とさずには直せないときは、無理に通さない。止まって、状況と選択肢をユーザーに報告する
6. カバレッジは「今より下げない」を基準にし、上がったら `fail_under` を引き上げる（ラチェット）。100% を目指すが、そのために 2〜4 を破らない

### 仕組み

| 層 | 何をするか | 効く場面 |
|---|---|---|
| 指示（CLAUDE.md の「品質検査」） | 原則の要点を書き、この文書へリンクする | 毎回読み込まれる |
| Stop フック | Claude が作業を終える前に `scripts/quality_gate.py` を回す。落ちたら終わらせず、失敗の内容と原則を返して直させる。検査を緩める変更を見つけたら、一度止めて見直させる | 数字を通したくなる瞬間（失敗した直後）に原則が届く |
| CI（`quality` ジョブ） | 同じ検査を `--ci` で回す | 手で直した変更や、フックの外での変更 |

検査の中身は ruff、pytest（カバレッジを測りながら）、カバレッジの基準（`fail_under`）の3つ。

Stop フックは、HEAD（最後のコミット）からの変更のうち、次のものを「検査を緩める変更」として見直させる。

- `pyproject.toml` の基準が緩んだ。`fail_under` を下げた、`branch` を切った、ruff の `select` から消した、ruff の `ignore`・`per-file-ignores`・`exclude` やカバレッジの `omit`・`exclude_lines`・`exclude_also` に足した、pytest の `addopts` を変えた、など
- `pyproject.toml` より優先される設定ファイル（`.coveragerc`、`setup.cfg`、`tox.ini`、`pytest.ini`、`ruff.toml`）がある
- `# noqa`・`# pragma: no cover`・skip / xfail がファイルの中で増えた。中身ごとに数えるので、理由の書き直しは数えない。文字列の中も数えない
- テスト関数がファイルの中で減った

止める（`decision: block`）のは、同じ指摘につき1回まで。Claude が直せずにもう一度止まろうとしたとき（`stop_hook_active`）は止めない。止め続けるとループになるためで、代わりに `systemMessage` でユーザーに直接知らせる。こうすると、Claude の報告に頼らずにユーザーが状態を知れる。

コメントで黙らせるものに理由があるかは、`tests/test_quality_gate.py` が全ファイルについて検査する（CI でも回る）。

## 却下した案

- **skill で検査させる**: skill は呼ばれたときに読む手順書で、いつ呼ぶかはモデルが判断する。急いでいるときに飛ばされる
- **全体のカバレッジ 100% を合格ラインにする**: 導入時は 87%。いきなり合格ラインにすると、原則 2〜4 を破る圧力がかかる。ラチェットで少しずつ上げる
- **検査を緩める変更を CI で失敗にする**: ユーザーが了承した正当な変更まで止まる。了承は会話で取り、CI では止めない
- **LLM に差分を判定させるフック（prompt 型・agent 型）**: Stop では使えない（ツールのイベント専用）。編集のたびに回すと遅く、費用もかかる

## 限界

- assert を弱める変更（`assert x == 3` を `assert x` にするなど）は、機械では見分けられない。原則 2 と差分のレビューに頼る
- 見直しは HEAD との差分しか見ないので、コミット済みの変更はフックでは見つからない。コミットはユーザーの指示で行う前提
- `.claude/settings.json` のフック自体を外されると、ローカルでは回らない。最後の砦は CI
- 今後の候補: 変更した行だけのカバレッジ（diff coverage）、mutation testing でテストの質を定期的に測る、PostToolUse で編集のたびに ruff をかける

## 影響

- 開発用の依存に ruff と coverage を足した（ランタイム依存は httpx のまま）
- `fail_under` を上げたら、[QUALITY_SCORE.md](../QUALITY_SCORE.md) のカバレッジの記録も直す
- フックは Git Bash（Windows）か bash で動く。`.venv` がないとフックはエラーを出して止めない
