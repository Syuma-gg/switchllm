# 品質検査の方針

品質検査（ruff・pytest・カバレッジ）は、品質を上げるための手段である。検査の数字を通すために品質を落とさない。

この文書は、ハーネスのテンプレート（quality-gate）の一部で、どのプロジェクトでも同じものを置く。Claude Code が検査に落ちたとき、ここを読んで直す。

## 原則

1. 検査は品質を上げるための手段。数字を通すことを目的にしない
2. テストには振る舞いを確かめる assert を書く。行を実行するだけのテストは書かない。テストを書いて見つかった不具合は直す
3. 基準（`fail_under`、ruff のルール、カバレッジやテストの除外）を緩めない。緩める必要があると考えたら、理由を説明してユーザーの了承を得る
4. `# noqa`・`# pragma: no cover`・`pytest.mark.skip` / `xfail` は、品質上の理由があるときだけ使う。コメントで書くものには、同じ行に理由を書く（例: `# noqa: B006 - 可変の既定値でも任意の引数として扱えるか確かめる`）。使ったことは作業の報告で伝える
5. 品質を落とさずには直せないときは、無理に通さない。止まって、状況と選択肢をユーザーに報告する
6. カバレッジは「今より下げない」を基準にし、上がったら `fail_under` を引き上げる（ラチェット）。100% を目指すが、そのために 2〜4 を破らない

AI にコードを書かせると、検査を満たす一番の近道を選びやすい。行を実行するだけのテストを書く、`# noqa` で黙らせる、基準の値を下げる、落ちるテストを消す、などである。どれも検査は通るが、品質は上がらないか、かえって下がる。原則はこれを防ぐためにある。

## 仕組み

| 層 | 何をするか | 効く場面 |
|---|---|---|
| 指示（CLAUDE.md の「品質検査」） | 原則の要点を書き、この文書へリンクする | 毎回読み込まれる |
| Stop フック（`.claude/settings.json`） | Claude が作業を終える前に `scripts/quality_gate.py` を回す。落ちたら終わらせず、失敗の内容と原則を返して直させる。検査を緩める変更を見つけたら、一度止めて見直させる | 数字を通したくなる瞬間（失敗した直後）に原則が届く |
| CI | 同じ検査を `python scripts/quality_gate.py --ci` で回す | 手で直した変更や、フックの外での変更 |

検査の中身は次の3つ。どのファイルを検査するか、基準の値は、`pyproject.toml` の各ツールの設定で決まる。

- ruff（プロジェクト全体から、ruff の設定で除外したものを除く）
- pytest（カバレッジを測りながら）
- カバレッジの基準（`[tool.coverage.report]` の `fail_under`）

Stop フックは、HEAD（最後のコミット）からの変更のうち、次のものを「検査を緩める変更」として見直させる。

- `pyproject.toml` の基準が緩んだ。`fail_under` を下げた、`branch` を切った、ruff の `select` から消した、ruff の `ignore`・`per-file-ignores`・`exclude` やカバレッジの `omit`・`exclude_lines`・`exclude_also` に足した、pytest の `testpaths` から消した、`addopts` を変えた、など
- `pyproject.toml` より優先される設定ファイル（`.coveragerc`、`pytest.ini`、`ruff.toml`、検査の節がある `setup.cfg`・`tox.ini` など）がある
- `# noqa`・`# pragma: no cover`・skip / xfail がファイルの中で増えた。中身ごとに数えるので、理由の書き直しは数えない。文字列の中も数えない
- テスト関数がファイルの中で減った

止める（`decision: block`）のは、同じ指摘につき1回まで。Claude が直せずにもう一度止まろうとしたとき（`stop_hook_active`）は止めない。止め続けるとループになるためで、代わりに `systemMessage` でユーザーに直接知らせる。

コメントで黙らせるものに理由があるかは、`tests/test_quality_gate.py` がプロジェクトの全ファイルについて検査する（CI でも回る）。

## 検査に落ちたとき

| 落ちた検査 | 直し方 | してはいけないこと |
|---|---|---|
| ruff | 指摘された書き方を直す。ルールの意図が分からなければ `ruff rule <コード>` で読む | `# noqa` や `ignore` で黙らせる（品質上の理由があり、同じ行に書けるときを除く） |
| pytest | 失敗したテストが確かめている振る舞いを読み、コードとテストのどちらが正しいかを判断して直す | テストを消す、skip にする、assert を弱める |
| カバレッジ | `Missing` 列の行が、どの振る舞いのためにあるかを読み、それを確かめるテストを足す。どこからも使われない行なら、コードを消す | 結果を確かめないテストで行を通す、`# pragma: no cover` や `omit` で外す |

## 見直しを求められたとき

フックが「検査を緩める変更」を報告したら、品質のために必要な変更かを考える。

- 必要なら残してよい。理由を作業の報告でユーザーに伝える。基準を緩める変更は、ユーザーの了承を得る
- 数字を通すためだけの変更なら取り消し、テストかコードで直す

## 基準を変えるとき

- 厳しくする変更（`fail_under` を上げる、ruff のルールを足す）は、いつでもしてよい
- カバレッジが上がったら、測った値の小数を切り捨てて `fail_under` に入れる
- 緩める変更は、理由を説明してユーザーの了承を得てから行う。了承を得たら、理由を `pyproject.toml` のコメントか設計の文書に残す

## 限界

- assert を弱める変更（`assert x == 3` を `assert x` にするなど）は、機械では見分けられない。原則 2 と差分のレビューに頼る
- 見直しは HEAD との差分しか見ないので、コミット済みの変更はフックでは見つからない
- サブフォルダーに置いた設定ファイル（`tests/ruff.toml` など）や、`conftest.py` でテストを外す書き方は見ていない
- `.claude/settings.json` のフック自体を外されると、ローカルでは回らない。最後の砦は CI
