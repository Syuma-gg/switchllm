## 公開の設定

Trusted Publishing（OIDC）を使うので、API トークンを作って secret に入れる必要はない。PyPI と TestPyPI はアカウントが別。

| どこで | 何をする | 値 |
|---|---|---|
| PyPI（https://pypi.org/manage/account/publishing/） | pending publisher を足す | PyPI Project Name `switchllm` / Owner `Syuma-gg` / Repository name `switchllm` / Workflow name `publish.yml` / Environment name `pypi` |
| TestPyPI（https://test.pypi.org/manage/account/publishing/） | pending publisher を足す | 上と同じで、Environment name だけ `testpypi` |
| GitHub（リポジトリの Settings → Environments） | environment を2つ作る | `pypi`（Deployment branches and tags を Tag の `v*` に限る。Required reviewers に自分を入れる。PyPA のガイドが、PyPI に上げるたびに手で承認することを求めている）と `testpypi`（承認は要らない。限るなら Branch の `main`）。secret と variable は要らない。2026-11-15 に Private のまま `pypi` を作ったところ、承認者を設定する欄（Deployment protection rules）が出なかった。GitHub は Private リポジトリでの承認者を上位のプランに限っているためとみられるので、Public にしてから設定する |

公開の順番:

1. リポジトリを Public にする（上の手順）
2. Actions の「publish」を「Run workflow」で実行し、TestPyPI に上げる。新しい venv で `pip install -i https://test.pypi.org/simple/ --extra-index-url https://pypi.org/simple/ switchllm` が入ることを確かめる（httpx は TestPyPI にないので、本家の PyPI から取る）。TestPyPI は同じ版を上げ直せないので、やり直すときは版を変える
3. `CHANGELOG.md` の「0.1.0（未公開）」を公開日に書き換えてコミットし、push する
4. GitHub で Release を作る。タグは `v0.1.0`（`__version__` と違うと、ワークフローが止まる）。公開すると publish が走り、`pypi` の承認を待つので、承認する

- 2026-11-15: TestPyPI へは手動の実行（`workflow_dispatch`）で、PyPI へは Release の公開で上げる。PyPA のガイドは push のたびに TestPyPI へ上げる形だが、TestPyPI は同じ版を上げ直せないので、2回目以降の push が毎回失敗するため
- 2026-11-15: Release のタグ（`v<版>`）と、ビルドした sdist の版が違ったら公開しない。版の正本は `__version__` なので、タグだけを変えて別の版として上げてしまうのを防ぐ
- 2026-11-15: 公開の前に、ビルドした配布物そのもので全テストを回すジョブ（`test-dist`）を挟む。`MANIFEST.in` の入れ漏れや、wheel に入らないファイルへの依存は、リポジトリのテストでは見つからないため
